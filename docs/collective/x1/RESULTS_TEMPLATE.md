# X1 sealed results: template (frozen at B2a)

This is the pre-written template for `docs/collective/x1/RESULTS.md`. It was committed with B2a, before any seed,
prereg, plant spec or outcome of the sealed run existed, and it is never edited afterwards. `RESULTS.md` follows its
sections in order (below the catalog). Every value `RESULTS.md` shows is a pointer row into a committed run file, every
interpretation bullet is selected mechanically from the catalog by the stored scorecard, and any other prose goes only
under the last heading, `Post-hoc notes (written after the results)`, where it cites values only through pointer rows.

**Claim wording.** When `verdict.pass` is true, say "meets STRATEGY 11.2's bar on a synthetic, same-author plant";
never "X1 passed" or any phrase that says the X1 experiment of STRATEGY section 11.2 is met. `x1.counts_as_strategy_x1`
is shown as stored.

## Catalog

The first `json` block of this file is the machine-readable catalog: the sentences that always appear (`always`), the
governing-interval and multiple-comparisons texts, the interpretation sentences in the order they appear and the
conditions that select them (`interpretations`), the row groups in the order they appear (`rows`), and the format
rules (`format`).

## Sections of RESULTS.md, in order

### `# X1 sealed results: synthetic, same-author, internal only`

One short paragraph saying what the file is: the first and only evaluation of the sealed specs, at the seal commit,
reported through this template.

### `## Fixed statements`

The six `always` sentences, verbatim, as bullets, in catalog order, then the `governing_interval` sentence verbatim.

### `## Protocol`

The `Protocol` row group: the freeze and prereg commits, the code hash, the family size, the ten seeds, the
planter's call counts (as the wrapper logged them and as the planter declared them), the tool-log hash and whether the
declaration is self-reported only, and each pack's spec size. A mismatch between the logged and declared call counts is
shown, never smoothed over.

### `## <pack>` (device_quality first, then claims_integrity)

- `### Primary endpoint`: the `Primary endpoint` rows.
- `### Interpretation: <pack>`: one bullet per catalog interpretation whose conditions all hold on that pack's stored
  scorecard, in catalog order, with `{pack}` filled in; nothing else.
- `### Channels`, `### Strata`, `### Decoys`, `### Lifts`, `### By construction and warnings`,
  `### Stamps and provenance` and `### Cost`: the row groups of the same names.

### `## Multiple comparisons`

The `multiple_comparisons` paragraph, verbatim.

### `## Lab handoff`

The `Lab handoff` rows (each pack's fixture and prereg, with their sha256), then these points:

- the commands are `check-plant --construct` and `run --dry-run`, then `run` with the prereg's ten seeds;
- the sealed specs bind only to these preregs, so a prereg the lab makes is refused (`prereg_sha256`);
- `run` needs every prereg seed, `eval_code_hash()` equal to the SEAL `code_hash`, unchanged pack hashes and a clean
  tree; any later change to `EVAL_CODE_FILES` or to the packs' hashed files makes `run` refuse, so replay at the seal
  commit;
- the lab's x1 adapter runs the harness's lexical X, so no model is involved; a real-model X1 needs collective-side
  extractor code that is not built;
- `lab.sim`'s plant registry is device_quality-only and sized for fewer weeks; the specs need 6 sites, 104 weeks and
  evaluation weeks 26 to 103, so the lab needs changes there; the local cost per seed is in the `Cost` rows;
- claims_integrity has no `lab.sim` path;
- E2 can load the fixtures with `--x1-prereg docs/collective/x1/<pack>/prereg.json`;
- the holdout is now spent for detector development: any later detector change evaluated on these specs is post-hoc.

### `## Post-hoc notes (written after the results)`

Last. Anything written after the results were seen, labelled as such, citing values only through pointer rows.
